# API 限流与配额管理（Rate Limiting & Throttling）

## 1. 默认限流策略
- 每个 API Key 默认 QPS 上限（示例：100 QPS，突发桶 200）
- 超过限额返回 `429 Too Many Requests`，响应头包含 `Retry-After`

## 2. 常见 429 排查步骤
1. 检查调用方是否有突发流量（批量任务、重试风暴）
2. 检查是否多个服务共用同一 API Key 导致额度被瓜分
3. 查看限流监控面板，确认是否命中的是全局限流还是单接口限流

## 3. 申请更高配额
- 提交配额提升申请，说明业务场景、预计峰值 QPS、增长趋势
- 涉及核心网关/共享资源的配额提升，需按变更管理流程走审批（视为常规或重大变更）
- 临时大促/压测场景可申请"临时配额"，到期自动恢复默认值

## 4. 限流算法说明（供排查参考）
- 令牌桶（Token Bucket）：允许一定程度突发，超过桶容量才限流
- 滑动窗口（Sliding Window）：更平滑地统计单位时间请求数，避免边界突刺

## 5. 最佳实践
- 客户端应实现指数退避重试（Exponential Backoff），避免 429 后立即重试加剧限流
- 对关键业务接口，建议提前评估容量并预先申请合理配额，而不是等触发限流再申请
